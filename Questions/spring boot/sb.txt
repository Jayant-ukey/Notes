
Que 1 : What are starter dependencies in Spring Boot
Ans :- Starter dependencies in Spring Boot are pre-configured dependency descriptors that simplify project setup. Instead of adding multiple individual dependencies manually, Spring Boot provides starter packages that bundle commonly used libraries together for a specific functionality.

For example:
	</xml>
	
	<dependency>
		<groupId>org.springframework.boot</groupId>
		<artifactId>spring-boot-starter-web</artifactId>
	</dependency>
	
	
This single starter automatically includes:
	- Spring MVC
	- Embedded Tomcat
	- Jackson for JSON processing
	- Validation libraries
	- Logging dependencies

So we don’t need to configure everything manually.

Commonly Used Starter Dependencies
	- spring-boot-starter-web → REST APIs & microservices
	- spring-boot-starter-data-jpa → Database operations using Hibernate/JPA
	- spring-boot-starter-security → Authentication & authorization
	- spring-boot-starter-test → Unit & integration testing
	- spring-boot-starter-actuator → Monitoring & health checks
	- spring-boot-starter-validation → Request validations
	- spring-cloud-starter-openfeign → Inter-service communication in microservices

Why They Are Important:
	Starter dependencies help maintain dependency compatibility, reduce configuration effort, and speed up development. Since Spring Boot manages dependency versions internally, it avoids version conflicts and makes applications production-ready faster.
	
	In enterprise projects, starter dependencies are especially useful in microservices because they standardize configurations across services and reduce boilerplate setup.
	
	
sub que :- How does Spring Boot manage dependency versions?
ans - Spring Boot uses a parent POM called spring-boot-starter-parent, which provides dependency management and compatible versions for all Spring libraries.

Que :  Difference between @controller and @RestController

Ans: - @Controller and @RestController are both Spring MVC annotations used to handle HTTP requests, but the main difference is in how the response is returned.

@Controller:
	@Controller is mainly used in traditional Spring MVC applications where we return view pages like JSP, Thymeleaf, or HTML.
	
	Example:
		@Controller
		public class HomeController {

			@GetMapping("/home")
			public String home() {
				return "home";
			}
		}

	
	Here:
	- "home" is treated as a view name
	- Spring resolves it to a JSP/HTML page
	
	
@RestController
	@RestController is used in REST APIs and microservices. It returns data directly as JSON or XML instead of returning a view.
	
	Example:
		@RestController
		public class EmployeeController {

			@GetMapping("/employee")
			public Employee getEmployee() {
				return new Employee(101, "Rahul");
			}
		}
		
	
	Here:
		Response is automatically converted into JSON using Jackson
		
	
	
Internal Difference:
	@RestController is a combination of @Controller + @ResponseBody.
		
	Equivalent:
		@Controller
		@ResponseBody
		public class EmployeeController {
		}


Real-Time Usage 
	- “In microservices architecture, we mostly use @RestController because services communicate through REST APIs returning JSON responses.”
	- “@Controller is generally used in monolithic or MVC-based applications where server-side rendering is required.”

Que : What is @RequestMapping

Ans:- @RequestMapping is used to map incoming HTTP requests to specific handler methods or controller classes in Spring MVC and Spring Boot.

Example:
	@RestController
	@RequestMapping("/employees")
	public class EmployeeController {

		@RequestMapping("/all")
		public String getEmployees() {
			return "Employee List";
		}
	}
	
Here:
	/employees → class-level mapping
	/all → method-level mapping
	
	Final endpoint becomes: /employees/all
	

HTTP Method Mapping
	@RequestMapping can also define HTTP methods like GET, POST, PUT, DELETE.
	
	Example:
	@RequestMapping(value="/employee", method=RequestMethod.GET)
	public String getEmployee() {
		return "Employee";
	}
	
	
Modern Approach 
	In modern Spring Boot applications, instead of using @RequestMapping for every method, we usually use specialized annotations like:

		@GetMapping
		@PostMapping
		@PutMapping
		@DeleteMapping
		
	Example: 
	@GetMapping("/employee")
	public Employee getEmployee() {
		return employeeService.getEmployee();
	}
	
	These annotations improve readability and reduce boilerplate code.

	
Real-Time Microservices Usage
	“In microservices, @RequestMapping is commonly used at class level to define a base URI for a service module, while method-level mappings define specific REST endpoints.”
	
	example:
		@RestController
		@RequestMapping("/api/v1/orders")
		public class OrderController {
		}
		

Advanced Points:-

	“@RequestMapping supports:

	- Path variables
	- Request parameters
	- Headers
	- Content type mappings (consumes and produces)
	- Multiple URL patterns”
	
	Example:
	@RequestMapping(
		value="/orders",
		method=RequestMethod.POST,
		consumes="application/json",
		produces="application/json"
	)

Que: Difference between @GetMapping and @PostMapping.

Ans:- @GetMapping and @PostMapping are specialized Spring annotations used for handling different HTTP request methods in REST APIs.

@GetMapping
	“@GetMapping is used to retrieve data from the server.”
	
	Characteristics
		- Used for fetching/read operations
		- Data is usually passed through path variables or query parameters
		- Should not modify server state
		- HTTP Method = GET
		
		
	Example:
		@GetMapping("/employees/{id}")
		public Employee getEmployee(@PathVariable int id) {
			return employeeService.getEmployee(id);
		}
		
		
	Real-Time Usage
		- Fetch employee details
		- Get order information
		- Search APIs
		- Read-only operations
		
	

@PostMapping:
	“@PostMapping is used to send data to the server and create resources.”

	Characteristics
		- Used for create operations
		- Request data is generally sent in request body
		- Modifies server state
		- HTTP Method = POST
	
	Example:
	@PostMapping("/employees")
	public Employee addEmployee(@RequestBody Employee employee) {
		return employeeService.save(employee);
	}
	
	Real-Time Usage
		- Create employee
		- Place order
		- User registration
		- Upload data
		

Important REST API Concept
	“GET requests should be safe and idempotent, meaning they should not change application data. POST requests are generally used for resource creation and can change server state.

Que:- @conditional annotation in spring boot

Ans:- “@Conditional in Spring Boot/Spring Framework is used to conditionally load beans or configurations based on specific conditions at runtime.”
	“It provides flexibility to enable or disable configurations depending on environment, properties, classpath, OS, or custom logic.”
	
	
syntax:
	@Configuration
	@Conditional(MyCondition.class)
	public class AppConfig {
	}
	
Here, MyCondition is a custom class implementing Condition interface.

As per GFG:

Spring Framework offers conditional annotations that control bean creation based on specific conditions. These annotations make applications adaptable to different environments without adding unnecessary code. They belong to the org.springframework.context.annotation and org.springframework.boot.autoconfigure.condition packages and rely on the @Conditional mechanism.

1. @Conditional
Used to register beans only when a custom condition is met. The condition logic is defined in a class implementing the Condition interface.

import org.springframework.context.annotation.*;

@Configuration
public class MyConfiguration {

    @Bean
    @Conditional(MyCondition.class)
    public MyBean myBean() {
        return new MyBean();
    }
}

Here, MyCondition defines whether the MyBean should be created.


Common Conditional Annotations in Spring Boot:
	“Spring Boot provides many predefined conditional annotations built on top of @Conditional.”
	

| Annotation                   | Purpose                       |
| ---------------------------- | ----------------------------- |
| `@ConditionalOnClass`        | Load if class exists          |
| `@ConditionalOnMissingBean`  | Load if bean not present      |
| `@ConditionalOnBean`         | Load if bean exists           |
| `@ConditionalOnProperty`     | Load based on property value  |
| `@ConditionalOnMissingClass` | Load if class absent          |
| `@ConditionalOnExpression`   | Load based on SpEL expression |

Que:- What is microservice architecture?

Ans:- Microservice architecture is an architectural style where an application is divided into multiple small, independently deployable services. Each microservice is focused on a specific business capability and communicates with other services using lightweight protocols like REST APIs, Kafka, or messaging queues.

Key Characteristics
1. Independent Services
	“Each service can be developed, deployed, and scaled independently.”

	Example:
		- User Service
		- Order Service
		- Payment Service
		- Inventory Service
		
2. Loosely Coupled:- “Services are loosely coupled, meaning changes in one service should minimally impact others.”

3. Separate Database:- “Typically each microservice owns its own database to maintain autonomy.”

4. Independent Deployment :- “Teams can deploy services separately without deploying the entire application.”

5. Technology Flexibility :- “Different services can use different technologies if required, although in most enterprise systems we standardize on Spring Boot.”

Real-Time Example
	“For an e-commerce application:
		- Product Service manages products
		- Order Service handles orders
		- Payment Service processes payments
		- Notification Service sends emails/SMS

All services communicate through REST APIs or asynchronous messaging like Kafka.”


| Monolith           | Microservices                 |
| ------------------ | ----------------------------- |
| Single application | Multiple independent services |
| Single deployment  | Independent deployments       |
| Tight coupling     | Loose coupling                |
| Harder to scale    | Easily scalable               |



Practical Perspective:-
	“In production systems, we generally use API Gateway for routing, Eureka for service discovery, centralized logging with ELK, distributed tracing, and Kubernetes for orchestration.”
	

Short Answer:
	“Microservice architecture is a design approach where an application is split into small independent services, each handling a specific business capability and communicating through APIs or messaging systems.”

		avoid code changes per environment,

Ans:- 
Expected Interview Answer:
	“Spring Boot performance optimization can be done at multiple levels — application startup, database, JVM, APIs, microservice communication, threading, caching, and monitoring. In production systems, we usually identify bottlenecks first using profiling and metrics, then optimize accordingly.”

full:
	
When we talk about optimizing Spring Boot performance, optimization can happen at multiple levels such as database layer, application layer, JVM level, API design, and microservice communication. In real projects, the first step is always identifying the bottleneck using monitoring and profiling tools instead of doing random optimizations.

In most applications, the database becomes the primary bottleneck, so query optimization plays a very important role. We usually optimize SQL queries, create proper indexes, avoid unnecessary joins, and use pagination for large datasets. In JPA or Hibernate, we also avoid the N+1 query problem and fetch only required data using DTO projections instead of loading complete entities.

Connection pooling is another important area. Spring Boot uses HikariCP by default, which is a high-performance connection pool. We configure the pool size based on application traffic and database capacity so that database connections are reused efficiently instead of creating new connections for every request.

Caching is one of the most effective ways to improve performance. Frequently accessed data can be cached using Redis or Caffeine so that repeated database calls are reduced. In many microservice applications, caching significantly reduces response time and improves scalability.

For time-consuming operations, asynchronous processing helps improve application responsiveness. Instead of blocking the main request thread, operations like email sending, report generation, or event processing can be handled asynchronously using @Async, custom thread pools, or messaging systems like Kafka.

At the API level, we optimize payload size and avoid sending unnecessary data in JSON responses. Compression such as GZIP can also be enabled to reduce network transfer time. Proper API pagination and lightweight DTOs help improve response performance.

JVM tuning is also important for high-traffic applications. We monitor heap memory usage, garbage collection behavior, and GC pause times. Based on application load, we tune JVM parameters like heap size and garbage collector configuration. G1GC is commonly used in modern Spring Boot applications because it provides better performance for large heap sizes.

In microservices architecture, performance is also affected by inter-service communication. Too many synchronous REST calls can increase latency, so in some scenarios asynchronous communication using Kafka or RabbitMQ is preferred. We also use resilience patterns like circuit breakers, retries, and bulkheads to improve stability and avoid cascading failures.

Monitoring and observability are extremely important in performance optimization. We use Spring Boot Actuator, Micrometer, Prometheus, Grafana, and distributed tracing tools to monitor response times, memory usage, CPU utilization, thread counts, and API latency. Performance optimization should always be metrics-driven because without proper monitoring it is difficult to identify the real bottleneck.

Overall, Spring Boot optimization is not about a single change. It is a combination of database tuning, efficient coding practices, caching, asynchronous processing, JVM tuning, proper monitoring, and optimized microservice communication.


---------

Hibernate performance optimization mainly focuses on reducing unnecessary database interaction, improving query efficiency, and managing entity loading properly. In most real-world applications, poor Hibernate configuration or improper entity design can create major performance issues even if the database itself is optimized.

One of the most common performance problems in Hibernate is the N+1 query issue. This happens when Hibernate executes one query to fetch parent records and then executes additional queries for each child entity. To avoid this, we use fetch joins, entity graphs, or batch fetching so that related data is loaded efficiently in fewer queries.

Lazy loading and eager loading should be used carefully. By default, relationships should generally be lazy-loaded because eager loading may fetch unnecessary data and increase memory consumption. However, if related data is always required, then fetch joins can be used to reduce multiple database calls.

Fetching complete entities when only a few fields are needed also affects performance. In such cases, DTO projections are preferred because they reduce memory usage and improve query execution time. Instead of loading the entire entity object, only the required columns are fetched from the database.

Batch processing is another important optimization technique. When inserting or updating large amounts of data, Hibernate should use batch inserts and batch updates instead of executing one SQL statement per row. This reduces database round trips and significantly improves performance for bulk operations.

The first-level cache provided by Hibernate works at the session level and helps avoid repeated database calls within the same transaction. In applications where frequently accessed data changes less often, second-level caching using tools like Redis or Ehcache can further improve performance by reducing database hits across multiple sessions.

Connection pooling also plays an important role. Spring Boot commonly uses HikariCP, which efficiently manages database connections and avoids the overhead of repeatedly opening and closing connections. Proper pool size configuration is necessary to balance throughput and database load.

Query optimization is critical in Hibernate. We should avoid writing inefficient JPQL or native queries, and proper database indexing must be used for frequently searched columns. Pagination should always be applied when handling large datasets to avoid loading excessive records into memory.

Hibernate generates SQL internally, so SQL logging and query analysis are useful for identifying slow queries. Tools like Hibernate statistics, Actuator metrics, and database execution plans help analyze performance bottlenecks.

Another important optimization is avoiding unnecessary flushing. Hibernate automatically synchronizes entity changes with the database, but excessive flushing can impact performance. Proper transaction boundaries and controlled flushing improve efficiency.

In high-performance systems, read-only transactions can also be used for query operations because Hibernate skips dirty checking for entities in read-only mode, which reduces overhead.

Overall, Hibernate optimization is mainly about minimizing database round trips, controlling entity loading properly, optimizing queries, using caching effectively, and monitoring generated SQL to identify bottlenecks.

Que - What is transaction management?

Ans- Transaction management is used to maintain data consistency and integrity during database operations. A transaction is basically a group of operations that are treated as a single unit of work. Either all operations should be completed successfully, or if any operation fails, all previous operations should be rolled back so that the database remains in a consistent state.

For example, in a banking application, if money is deducted from one account and credited to another account, both operations must succeed together. If the credit operation fails after the debit is completed, the debit operation should also be rolled back. This is the main purpose of transaction management.

In Spring Boot, transaction management is commonly handled using the @Transactional annotation. When a method is marked as transactional, Spring creates a proxy around that method. Before the method execution starts, Spring opens a database transaction. If the method completes successfully, the transaction is committed. If any runtime exception occurs, the transaction is rolled back automatically.

Transaction management follows ACID properties. Atomicity ensures that all operations inside the transaction are completed together or rolled back together. Consistency ensures that the database remains in a valid state before and after the transaction. Isolation controls how multiple transactions interact with each other concurrently. Durability ensures that once a transaction is committed, the data is permanently saved even if the system crashes.

Spring supports both declarative and programmatic transaction management. Declarative transaction management using @Transactional is most commonly used because it is simpler and cleaner. Programmatic transaction management is used in complex scenarios where transactions need to be controlled manually.

Propagation and isolation levels are also important concepts in transaction management. Propagation defines how transactional methods behave when one transactional method calls another transactional method. For example, REQUIRED joins the existing transaction if present, while REQUIRES_NEW creates a completely new transaction.

Isolation levels define how transaction data is visible to other concurrent transactions. Different isolation levels help prevent issues like dirty reads, non-repeatable reads, and phantom reads. In most applications, the default isolation level provided by the database is sufficient, but high-concurrency systems may require tuning based on business requirements.

In microservices architecture, transaction management becomes more challenging because transactions may span across multiple services and databases. Traditional distributed transactions using two-phase commit are generally avoided due to performance and scalability issues. Instead, patterns like Saga are commonly used to maintain eventual consistency between microservices.

Overall, transaction management is very important for ensuring reliable, consistent, and failure-safe database operations in enterprise applications.

Que - Coding Transaction Example

Ans:
A common example of transaction management is a money transfer operation between two bank accounts. In this scenario, money should be deducted from one account and credited to another account within the same transaction. If any step fails, the entire transaction should be rolled back to maintain data consistency.

```java
@Service
public class BankService {

    @Autowired
    private AccountRepository accountRepository;

    @Transactional
    public void transferMoney(Long fromAccountId, Long toAccountId, double amount) {

        Account sender = accountRepository.findById(fromAccountId)
                .orElseThrow(() -> new RuntimeException("Sender account not found"));

        Account receiver = accountRepository.findById(toAccountId)
                .orElseThrow(() -> new RuntimeException("Receiver account not found"));

        if (sender.getBalance() < amount) {
            throw new RuntimeException("Insufficient balance");
        }

        sender.setBalance(sender.getBalance() - amount);
        receiver.setBalance(receiver.getBalance() + amount);

        accountRepository.save(sender);
        accountRepository.save(receiver);
    }
}
```

In this example, the @Transactional annotation ensures that both database operations are treated as a single transaction. If both save operations are completed successfully, the transaction is committed. If any exception occurs during execution, Spring automatically rolls back all database changes.

For example, if the sender balance is deducted successfully but an exception occurs before updating the receiver account, Hibernate and Spring rollback the transaction so that the deducted amount is restored automatically.

Internally, Spring uses AOP proxies for transaction management. When the transactional method is called, Spring opens a database transaction before method execution and commits or rolls back the transaction based on the outcome of the method execution.

This approach helps maintain data consistency and prevents partial updates in enterprise applications.

Rate limiting can be implemented to protect APIs from abuse, brute-force attacks, or excessive traffic. API gateways or tools like Resilience4j and Bucket4j are commonly used for this purpose.

In microservices architecture, API Gateway security is commonly used. Authentication and token validation are often centralized at the gateway level so that downstream services remain simpler and more secure.

Monitoring and logging are equally important for API security. Security events, failed login attempts, and suspicious activities should be logged and monitored using centralized logging and monitoring systems.

Overall, securing REST APIs in Spring Boot involves implementing authentication and authorization, encrypting sensitive data, validating input, securing communication using HTTPS, preventing common attacks, and continuously monitoring the system for suspicious activity.

Que - What is memory management in spring boot?

Ans- Memory management in Spring Boot refers to how a Spring Boot application uses and manages JVM memory during runtime, including how objects are created, stored, cleaned up, and optimized to avoid memory leaks and performance degradation.

Since Spring Boot applications run on the JVM, memory management is primarily handled by the JVM itself using heap memory, stack memory, and garbage collection. However, the way we design Spring Boot applications directly impacts how efficiently memory is used.

Most application objects such as Spring beans, service classes, repositories, and entities are stored in heap memory. The JVM uses garbage collection to automatically remove objects that are no longer referenced, but improper coding practices can still lead to memory leaks if objects are unintentionally retained.

In Spring Boot, memory issues often arise due to excessive object creation, improper caching, long-lived sessions, or holding large data structures in memory. For example, loading a large dataset into memory without pagination or streaming can quickly consume heap space and lead to OutOfMemoryError.

Spring Boot applications also use connection pools, caches, and thread pools, all of which consume memory. If these are not configured properly, they can lead to excessive memory usage or thread exhaustion.

Hibernate and JPA also play a role in memory management. If entities are loaded in large numbers without clearing the persistence context, they remain in the first-level cache (session-level cache), which can increase memory consumption. This is why batch processing and periodic flushing/clearing of sessions are important for large operations.

Spring Boot provides support for caching mechanisms like Ehcache or Redis, which can either improve performance or cause memory issues if not configured with proper eviction policies. Unlimited caching without TTL (time-to-live) can lead to memory bloat.

Garbage collection is a key part of memory management. The JVM automatically frees memory used by unreachable objects, but frequent object creation, heavy allocations, or memory leaks can trigger frequent GC cycles, which can degrade application performance. Common GC algorithms like G1GC are used in production Spring Boot applications for better throughput and predictable pause times.

Monitoring memory usage is an important part of managing Spring Boot applications. Tools like Spring Boot Actuator, VisualVM, JConsole, and Prometheus help track heap usage, GC activity, and memory trends so that potential issues can be detected early.

From a best practices perspective, memory management in Spring Boot involves writing efficient code, avoiding unnecessary object retention, using pagination for large data sets, properly configuring caches and connection pools, and monitoring JVM performance regularly.

Overall, memory management in Spring Boot is not just about the framework but about understanding JVM behavior, controlling object lifecycle, optimizing data handling, and ensuring the application runs efficiently under production load without memory leaks or excessive garbage collection overhead.

In a real application, pagination is important for performance because it reduces memory usage, improves response time, and avoids loading large amounts of data from the database in a single request.

For example, we first create a repository that extends `JpaRepository`, which already provides pagination support out of the box.

```java
public interface UserRepository extends JpaRepository<User, Long> {
}
```

```java 
@Service
public class UserService {

```

Finally, in the controller layer, we expose this as a REST API so that the client can request specific pages dynamically.

```java 
@RestController
@RequestMapping("/users")
public class UserController {

    @Autowired
    private UserService userService;

    @GetMapping
    public Page<User> getUsers(
            @RequestParam int page,
            @RequestParam int size) {

        return userService.getUsers(page, size);
    }
}
```

When a request comes like `/users?page=0&size=10`, the API returns only 10 records instead of fetching the entire dataset, which significantly improves performance when dealing with large tables.

Que - Coding : How to create a PUT api in spring boot

Ans- A PUT API in Spring Boot is used to update an existing resource completely. In RESTful design, PUT is idempotent, which means if we call the same request multiple times with the same data, the result will remain the same.

To create a PUT API, we typically define a REST controller, accept the updated request body using `@RequestBody`, and identify the resource using `@PathVariable`. Then we fetch the existing record from the database, update its fields, and save it back.

For example, consider updating a User entity.

First, we define the controller with a PUT endpoint.

```java 
@RestController
@RequestMapping("/users")
public class UserController {

    @Autowired
    private UserService userService;

    @PutMapping("/{id}")
    public ResponseEntity<User> updateUser(
            @PathVariable Long id,
            @RequestBody User updatedUser) {

        User user = userService.updateUser(id, updatedUser);
        return ResponseEntity.ok(user);
    }
}
```

Then in the service layer, we handle the update logic by first fetching the existing user from the database. If the user is not found, we throw an exception. Otherwise, we update the required fields and save the entity.

```java 
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    public User updateUser(Long id, User updatedUser) {

        User existingUser = userRepository.findById(id)
                .orElseThrow(() -> new RuntimeException("User not found"));

        existingUser.setName(updatedUser.getName());
        existingUser.setEmail(updatedUser.getEmail());
        existingUser.setAge(updatedUser.getAge());

        return userRepository.save(existingUser);
    }
}
```

In this example, the PUT API updates the full user record based on the provided ID. If the user exists, the fields are updated and saved; otherwise, an exception is thrown.

In real-world applications, we usually use DTOs instead of directly exposing entities. We also add validation using `@Valid` to ensure request data is correct. Additionally, proper exception handling is used to return meaningful HTTP status codes like 404 for "not found" scenarios.

Overall, a PUT API in Spring Boot is simply a combination of REST mapping, request handling, service-layer update logic, and repository save operation, with proper validation and error handling for production readiness.

```java
}
```

Here, `User` is the entity type and `Long` is the type of the primary key. Without writing any implementation, we automatically get built-in methods like:

* save()
* findById()
* findAll()
* deleteById()
* delete()
* count()

For example, we can use it in a service like this:

```java
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    public User createUser(User user) {
        return userRepository.save(user);
    }

    public List<User> getUsers() {
        return userRepository.findAll();
    }
}
```

JPA Repository also supports custom query methods using method naming conventions. For example:

```
List<User> findByName(String name);
```

Spring automatically converts this into a SQL query based on the method name.

We can also write custom queries using `@Query` annotation when complex queries are required.

Overall, JPA Repository is a powerful abstraction that reduces boilerplate code, improves productivity, and makes database operations cleaner, more readable, and easier to maintain in Spring Boot applications.

Que - Coding : How to create Entity class

Ans-
An Entity class in Spring Boot (using JPA/Hibernate) represents a table in the database. Each object of the entity class corresponds to a row in the table, and each field corresponds to a column. The entity class is used by Hibernate to perform ORM (Object Relational Mapping), so we don’t need to write SQL queries manually for basic operations.

To create an entity class, we use the `@Entity` annotation, and we must define a primary key using `@Id`. Usually, we also use `@GeneratedValue` to auto-generate the primary key value.

For example, a simple User entity class looks like this:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false)
    private String name;

    @Column(name = "email", unique = true)
    private String email;

    private int age;

    // getters and setters
}
```

In this example, `@Entity` tells Hibernate that this class is a database entity. The `@Table` annotation is optional and is used to specify the table name. If not provided, the class name is used as the table name by default.

The `@Id` annotation defines the primary key of the table, and `@GeneratedValue` defines how the primary key is generated, such as auto-increment in the database.

The `@Column` annotation is used to customize column properties like name, uniqueness, and nullability. If we do not specify it, Spring Boot automatically maps fields to columns with the same name.

Entity classes can also include relationships between tables using annotations like `@OneToOne`, `@OneToMany`, `@ManyToOne`, and `@ManyToMany`. For example, a User can have multiple Orders, which can be mapped using `@OneToMany`.

In real-world applications, entity classes are usually kept simple and focused only on persistence. Business logic is generally avoided inside entity classes to maintain clean architecture.

Overall, an entity class in Spring Boot is a core part of JPA that maps Java objects to database tables and enables ORM-based database interaction without writing raw SQL queries.

Que - Coding : How to return JSON repsone?

Ans - 
In Spring Boot, returning a JSON response is very simple because Spring Boot automatically uses Jackson (JSON converter) to convert Java objects into JSON format. Whenever we return an object from a REST controller, Spring internally serializes it into JSON and sends it as the HTTP response.

To return a JSON response, we typically use `@RestController`, which is a combination of `@Controller` and `@ResponseBody`. This ensures that whatever we return from the method is directly written into the HTTP response body as JSON.

For example, if we return a simple Java object, Spring Boot automatically converts it into JSON:

```java
@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping("/user")
    public User getUser() {

        User user = new User();
        user.setId(1L);
        user.setName("Rahul");
        user.setEmail("rahul@example.com");

        return user;
    }
}
```

In this example, the `User` object will be automatically converted into JSON like this:

```json 
{
  "id": 1,
  "name": "Rahul",
  "email": "rahul@example.com"
}
```

We can also return a `ResponseEntity` if we want to control HTTP status codes along with the JSON response. This is commonly used in real-world applications.

```java
@GetMapping("/user")
public ResponseEntity<User> getUser() {

    User user = new User();
    user.setId(1L);
    user.setName("Rahul");

    return ResponseEntity.ok(user);
}
```

If we want to return a list of objects, Spring Boot will automatically convert the list into a JSON array.

```java 
@GetMapping("/users")
public List<User> getUsers() {

    return List.of(
        new User(1L, "Rahul", "rahul@example.com"),
        new User(2L, "Amit", "amit@example.com")
    );
}
```

Spring Boot also allows customizing JSON responses using annotations like `@JsonIgnore`, `@JsonProperty`, and `@JsonInclude` from Jackson. These help control which fields should be included or excluded from the JSON output.

For example, if we don’t want to expose a password field:

```
@JsonIgnore
private String password;
```

Overall, returning JSON response in Spring Boot is very straightforward because of built-in Jackson support. We simply return Java objects from REST controllers, and Spring automatically converts them into JSON format for the client.
